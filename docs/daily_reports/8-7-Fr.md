### What I Learned
    Concepts:
     1. MuJoCo model versus simulation data

        MuJoCo model(MjModel) is a model that is described, built with many properties(body masses, geometry sizes, joint types, gravity constant). In a program, it is only compiled once from the XML(description of the model) and never change while running. So, any MuJoCo model is fixed/static.

        Simulation data(MjData) is everything that changes every timestep. Thus, Simulation data is mutable.
        One MuJoCo model includes many simulation data instances.

     2. MJCF and XML.

       MJCF is the abbrevation for: MuJoCo XML Configuration Format; It is MuJoCo's native scene-description language.

       XML(eXtensible Markup Language) is a text format for representing structured, hierarchical data using nested tags — similar spirit to HTML, but designed for data rather than documents, and with much stricter rules. "Extensible" means the tag names aren't fixed by a spec (unlike HTML's <div>, <p>, etc.) — each application defines its own vocabulary.

        Strict syntax rules:

              ● Every opening tag needs a matching closing tag, or must self-close with />.

              ● Tags must nest properly — no overlapping: <a><b></a></b> is invalid; must be <a><b></b></a>.

              ● Attribute values must be quoted: pos=0 0 1 (no quotes) is invalid; pos="0 0 1" is required.

              ● There's exactly one root element per file — for MJCF, that's always <mujoco>...</mujoco>, everything else nests inside it.
                  

       MJCF is that vocabulary for MuJoCo: tags like <mujoco>, <worldbody>, <geom> aren't part of XML itself, they're just names MuJoCo's developers chose.

     3. Simulation timestep
        
         MuJoCo advances physics in small fixed increments, not continuously. The default is 0.002 seconds (2ms) per mj_step call unless overridden in the XML with <option timestep="...">.

         In smoke test script: Every mj_step call increments data.time by exactly one timestep. Smaller timesteps → more accurate but slower; larger → faster but risk numerical instability (bouncing/exploding simulations), especially with contacts like your sphere hitting the plane.

     4. Viewer versus headless Execution
         
          -- Headless Execution
           
              running with no rendering at all;
              This is what actually matters for correctness: it's fast, scriptable, and works in any environment (servers, CI, your WSL box without GPU accel).

              E.g.
                  mujoco_smoke_test.py

          -- Viewer

              An interactive window(<python -m mujoco.viewer>) that renders the scene in real time for human eyes, using GLFW + OpenGL under the hood. It's a debugging/visualization convenience, not a correctness check — which is precisely why your handbook's "Common Mistakes" list warns against "treating the viewer as proof that the simulation is correct."

      6. qpos, qvel, ctrl, and time

           ● qpos — generalized position vector. For your free-joint sphere, that's 7 numbers: 3D position (x,y,z) + a quaternion (4 numbers) for orientation. For a simple hinge joint, it'd just be 1 number (the angle).

           ● qvel — generalized velocity vector, matching qpos's degrees of freedom (6 for a free joint — 3 linear + 3 angular; quaternions don't need a 4th velocity component since angular velocity is 3D).

           ● ctrl — the control input vector, one entry per actuator. Empty/irrelevant right now since your scene has zero actuators; you'll use this heavily in 3.3.

           ● time — data.time, incremented by timestep on every mj_step call — what your smoke test printed.

            •	What problems commonly occur when running the MuJoCo viewer under WSL?

                1. No display at all — DISPLAY environment variable missing

                    The most common failure on WSL setups without proper GUI forwarding: GLFW throws an error indicating the DISPLAY environment variable is missing, often followed by repeated "GLFW library is not initialized" errors and a segmentation fault. This happens when WSLg isn't active or DISPLAY isn't propagated to your shell — no window appears at all, not even a broken one. (You didn't hit this — a window did pop up, meaning your WSLg/X forwarding is working.)
                
                2. OpenGL context creation failure — gladLoadGL error

                    A related but distinct failure: the window/display connection works, but MuJoCo can't create a valid OpenGL context, throwing mujoco.FatalError: gladLoadGL error, generally paired with the same underlying GLFW/X11 complaint. The fix community consensus converges on is switching MuJoCo's rendering backend to EGL, since GLFW doesn't work in headless environments while OSMesa works but without GPU acceleration — you set this with an environment variable, e.g. MUJOCO_GL=egl.

                3. Software-rendering fallback — what I hit
                   
                   WSL has no GPU-accelerated OpenGL path, so it falls back to a CPU software rasterizer (llvmpipe). The window opens, but rendering is so slow it looks completely frozen — clicking the taskbar does nothing because the app isn't dead, just glacially slow. The "Warning: Copy mode" watermark you saw is WSLg's own display-forwarding layer flagging that it's also using an unaccelerated frame-copy path rather than efficient GPU passthrough.
                
                4. Wayland-specific glitches (WSLg uses a Wayland compositor internally)

                   Even when rendering does work, GLFW-based viewers under Wayland compositors (which is what WSLg runs internally) can show quirky behavior: borderless windows that display warnings about window position retrieval and cursor shape being unavailable, yet the program continues running normally, or in worse cases, the viewer freezing or crashing after running fine for a while, regardless of which rendering backend is specified. These tend to be intermittent and version-dependent — annoying to debug, not worth chasing down for this milestone.

            •	How can I verify MuJoCo headlessly when a GUI is unavailable?
                 
                 Level 1 -- Does it run at all 
                     My mujoco_smoke_test.py does this: load model, step N times, print a result with no window involved. This proves the pipeline works — install, load, step — but doesn't prove the physics is doing anything sensible. A model with a bug could still "run without crashing."

                 Level 2 -- Does the physics actually behave correctly? (numeric sanity checks)
                    Add assertions that check something physically meaningful happened — this is much stronger evidence than just "no crash":
{import mujoco

xml = """
<mujoco>
  <worldbody>
    <geom type="plane" size="1 1 0.1"/>
    <body pos="0 0 1">
      <joint type="free"/>
      <geom type="sphere" size="0.1"/>
    </body>
  </worldbody>
</mujoco>
"""
model = mujoco.MjModel.from_xml_string(xml)
data = mujoco.MjData(model)

z_start = data.qpos[2]
for _ in range(200):
    mujoco.mj_step(model, data)
z_end = data.qpos[2]

assert z_end < z_start, "Sphere did not fall — physics may be broken"
print(f"[PASS] sphere fell z={z_start:.3f} -> z={z_end:.3f} under gravity, t={data.time:.3f}s")}

                    Level 3 -- Offscreen rendering (visual proof, still no GUI/window)

                    This is the real answer to "verify visually without a GUI," and it's also your stretch goal ("save a short rendered video or frame sequence") for free. The key move: use mujoco.Renderer, not mujoco.viewer — Renderer draws into an off-screen buffer and returns pixel arrays, no window, no GLFW, no X11 dependency at all if you use the right backend:
{
import os
os.environ["MUJOCO_GL"] = "osmesa"  # set BEFORE importing mujoco

import mujoco
from PIL import Image

model = mujoco.MjModel.from_xml_path("/tmp/smoke_scene.xml")
data = mujoco.MjData(model)
renderer = mujoco.Renderer(model, height=480, width=640)

for _ in range(100):
    mujoco.mj_step(model, data)

renderer.update_scene(data)
pixels = renderer.render()
Image.fromarray(pixels).save("evidence/logs/headless_render.png")
print("[PASS] headless render saved to evidence/logs/headless_render.png")
}

       •	Explain qpos, qvel, and ctrl using a one-joint robot.
           One hinge joint, one number per quantity. That's what makes this the cleanest example: no free-joint quaternion complexity, just a single scalar for each.

           qpos — one number: the angle

           qvel — one number: how fast the angle is changing

           ctrl — one number: what you command

           ctrl is different in kind from the other two — it's an input you write, not state the simulator computes. It only exists if the joint has an actuator attached (a motor), and its meaning depends on the actuator type defined in the MJCF: for a simple motor actuator, ctrl[0] is a torque command in newton-meters. Setting data.ctrl[0] = 2.0 tells the motor "apply 2 N·m of torque," and then mj_step figures out how that torque changes qvel, and how qvel changes qpos — cause and effect flowing exactly one direction: ctrl → qvel → qpos.
